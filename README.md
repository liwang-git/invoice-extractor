# invoice-extractor

A small learning project: an LLM workflow that reads a plain-text invoice,
extracts fields to JSON, checks the numbers in code, and assigns an expense
category. It comes with an eval set, a cost/latency log, a small HTTP API and
a CI pipeline that fails the build when quality drops.

**Design rule: code decides, the model only reads.** Every accept, reject or
flag decision is plain Python in `extractor/validate.py`, never a prompt.

## How it works

1. **LLM step 1** extracts vendor, invoice number, date, line items, tax and total.
2. **Code checks** validate the schema (one retry on failure), then check that
   line items + tax = total. Problems are flagged for human review with a reason:
   `missing_total`, `total_mismatch`, `missing_invoice_number` or `invalid_output`.
3. **LLM step 2** assigns a category from a fixed list.
4. **Output** is JSON; evals and the API also log tokens, estimated cost and latency.

## Quick start

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt

pytest -q                       # unit tests (no network, no cost)
python run_evals.py             # eval set against the stub model (free)
```

## Models

`MODEL` picks the backend. Nothing in the code is tied to one model.

| `MODEL` | What it is |
|---|---|
| `stub` (default) | Returns the known answers. Free; used by tests and CI. `STUB_CORRUPT=0.3` makes it wrong 30% of the time, to watch the score drop. |
| `anthropic` | Anthropic API. Needs `ANTHROPIC_API_KEY` in the environment or a git-ignored `.env`. `ANTHROPIC_MODEL` overrides the model ID. |
| `bedrock` | Placeholder, not implemented yet. |

```bash
MODEL=anthropic python run_evals.py      # about $0.003 per run
EVAL_THRESHOLD=95 MODEL=anthropic python run_evals.py
```

`run_evals.py` exits 1 when accuracy is below `EVAL_THRESHOLD` (default 90).
That exit code is what lets CI fail a build. Each run writes
`runs/<timestamp>.jsonl` (git-ignored) with tokens, cost, latency and pass/fail
per case.

## API

```bash
uvicorn app:app --reload
curl -s -X POST http://127.0.0.1:8000/extract \
  -H 'Content-Type: application/json' \
  -d '{"text": "Acme Co.\nInvoice #A-1\nDate: 2026-10-14\n\nWidgets 10.00\n\nTotal 10.00"}'
```

With `MODEL=stub` only the eval invoices are recognised; use `MODEL=anthropic`
for arbitrary text. A flagged invoice is still HTTP 200, and `needs_review` in
the body says a human should look. Usage is logged to `runs/api-<date>.jsonl`
(metadata only, never invoice text).

## Eval set

`evals/cases/<id>/` holds a synthetic `invoice.txt` and its `expected.json`.
They are generated by `scripts/build_case.py`; edit that and rerun it rather
than editing the files by hand. All data is synthetic.

One case (`inv_019`, a discount shown only in the invoice footer) is a known
failure for the real model: it leaves the discount out of the line items, so
the pipeline flags a `total_mismatch`.

## CI

`.github/workflows/ci.yml` has two gates:

- **code**: tests plus the eval set against the stub (must be 100%). Every push and PR.
- **model**: the eval set against the real model (must be at least 95%).
  Runs only when `extractor/`, `evals/`, `run_evals.py`, the case generator,
  `requirements.txt` or the workflow itself change.

## Layout

```
extractor/        pipeline: validate.py, models.py, pipeline.py, pricing.py, usage_log.py
app.py            FastAPI app (POST /extract)
run_evals.py      eval runner and quality gate
evals/cases/      synthetic invoices and expected answers
scripts/          build_case.py generates the cases
tests/            pytest tests
```
